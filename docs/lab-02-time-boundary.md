# ЛР 2. Межа часової перевірки `OccurredAtUtc`

Умова з handler створення інциденту (`IncidentRules.IsOccurredAtTooFarInFuture`):

```csharp
occurredAtUtc > now.AddMinutes(5)   // true => дата недопустима
```

У робочому коді `now = DateTimeOffset.UtcNow` (годинник API не змінювався).
Для проби `now` фіксований: `2026-09-02T12:00:00Z`.

## 1. Вихідні дані

| Позначення | Значення | Відстань до межі `now + 5 хв = 12:05:00Z` |
|---|---|---|
| A | `2026-09-02T12:04:59.9999999Z` | −1 tick (−100 нс) |
| B | `2026-09-02T12:05:00Z` | 0 |
| C | `2026-09-02T12:05:00.0000001Z` | +1 tick (+100 нс) |

Один tick .NET = 100 нс — найменший крок `DateTimeOffset`, тому A і C є найближчими сусідами межі.

## 2. Статичний прогноз (зроблено ДО запуску)

| Точка | `> now+5` | Причина | Часова перевірка |
|---|---|---|---|
| A | false | A менша за межу, отже не більша | проходить |
| B | false | B дорівнює межі; строге `>` для рівних значень хибне | проходить |
| C | true | C більша за межу на 1 tick | порушує |

Межа включна: рівно `now + 5 хв` ще допустимо.

**Прогноз для заміни `>` на `>=`:** зміниться лише B (false → true), бо тільки для B значення дорівнює межі.
A строго менша, C строго більша — для них `>` і `>=` дають однаковий результат.

Це результат перевірки дати, а не обіцянка `201 Created`: запит можуть відхилити інші поля.

## 3. Матриця: правильна умова і два мутанти

- правильна: `occurredAtUtc > now.AddMinutes(5)`
- мутант 1: `occurredAtUtc >= now.AddMinutes(5)`
- мутант 2: `occurredAtUtc > now.AddMinutes(4)` (межа зсунута на 12:04:00Z, усі три точки пізніші за неї)

| Точка | правильна `> +5` | мутант 1 `>= +5` | мутант 2 `> +4` |
|---|---|---|---|
| A | false | false | **true** |
| B | false | **true** | **true** |
| C | true | true | true |

## 4. Мінімальний розрізнювальний набір: {A, B}

**Достатність.** Підписи умов на (A, B):

| Умова | (A, B) |
|---|---|
| правильна | (false, false) |
| мутант 1 | (false, true) |
| мутант 2 | (true, true) |

Усі три підписи різні, тож за результатами на A і B умову визначено однозначно.

**Неможливість меншого набору.** Одна точка дає одне булеве значення, тобто щонайбільше два різні
результати. Умов три, тому (принцип Діріхле) принаймні дві з них на будь-якій одній точці збігаються:
на A не розрізняються правильна і мутант 1, на B — мутанти 1 і 2, на C — усі три.

**Єдиність.** C дає `true` для всіх умов і нічого не розрізняє, тому {A, C} зводиться до A
(правильна = мутант 1), а {B, C} — до B (мутант 1 = мутант 2). Отже {A, B} — єдиний набір із двох точок.

## 5. Чому точна межа не вимірюється HTTP-запитом

Сервер порівнює `occurredAtUtc` з `UtcNow` у момент обробки запиту, а не надсилання. Затримка між ними
(мережа, черга, обробка) невідома і на порядки більша за 100 нс, тому влучити в межу з точністю до tick
неможливо, а результат біля межі не відтворюється. HTTP-сценарій (`tests/http/lab-02-checks.http`, T-07)
перевіряє лише явно далеку дату; точну межу перевіряє чисте порівняння з фіксованим `now`.
